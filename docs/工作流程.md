# openlist_strm_bridge 工作流程

## —— 系统生命周期、同步及冗余自愈执行流

---

## 一、 启动初始化与自同步生命周期 (核心时序)

程序在启动时，必须严格遵循以下时序，以确保数据库、物理磁盘与云端配置的绝对一致，防止出现时序错乱导致的数据库死锁或文件误删。

```text
    [ 步骤 1 ]  准备环境并初始化数据库 (确保核心表与索引 100% 建立)
        │
    [ 步骤 2 ]  加载引擎配置 (从 Admin API 获取 STRM 存储映射)
        │
    [ 步骤 3 ]  B 区物理磁盘逆向自同步 (盘点物理现状，重建、迁移或自愈)
        │
    [ 步骤 4 ]  同步受保护根目录并扫描已移除根目录
        │
    [ 步骤 5 ]  持久化当前根目录快照
        │
    [ 步骤 6 ]  A 区物理磁盘全量扫描与索引建立 (仅 STRM 文件；字幕由独立扫描处理)
        │
    [ 步骤 7 ]  A -> B 全量同步 (仅复制 B 区不存在的指纹，打分器过滤劣质命名)
        │
    [ 步骤 8 ]  启动双向 Watchdog 监控与主动刷新定时线程
```

> **设计原则：冗余清理永远只在局部触发，不做全盘扫描。** 启动时不再执行 `cleanup_a_redundant_using_api()` 和 `cleanup_b_redundant()`。冗余清理改为运行时按需触发：WebUI 手动刷新媒体时、watchdog 检测到 A/B 区文件删除时（通过 `trigger_delayed_cleanup`）。

## 二、 启动各阶段详细逻辑

## 阶段一：环境准备与数据库自检

- 创建或更新 `a_strm_files`, `b_strm_files`, `strm_identity`, `c_ghost_files`, `subtitles` 等表结构与索引。
- 数据库使用 WAL 模式 (`PRAGMA journal_mode=WAL`)，提升并发性能。

## 阶段二：引擎配置加载

- 登录 OpenList Admin API，获取存储设备列表
- 解析 `addition` 字段，提取 `SaveStrmLocalPath` 和 `paths`
- 构建本地 A 区路径与 STRM 引擎挂载点的映射表

## 阶段三：B区物理磁盘逆向自同步（血统大清洗）

程序在加载引擎配置后，对本地 B区 进行全量底细盘点，确保数据库是物理磁盘的"真实投影"：

1. **收集指纹**：遍历 B区 所有 `.strm` 文件，读取内容并计算指纹。
2. **入库纯新增**：如果在磁盘上发现了指纹，但数据库 B 表中无记录，判定为用户离线拷入的新 strm，血统校验通过后直接写入 B 表并标记为 `valid`。
3. **自愈与自同步（清理失效路径与重命名记录）**：
   - 如果数据库中记录了某条 B区路径，但物理磁盘上既没有这个文件，也没有任何同指纹的"同义路径"（仅改了文件名但内容相同的文件）。
   - 程序将执行 **"B区自同步清理"**：从数据库 B 表和 identity 表中将该失效路径彻底抹除，并在日志中登记。
   - 如果在磁盘上找到了同指纹但不同名字的"同义路径"，程序自动在数据库中执行 `move_b_record`，顺畅完成改名追踪。

## 阶段四：同步受保护根目录

- 从 `strm_engine_paths` 同步受保护根目录到数据库
- 扫描并清理已移除的受保护根目录（迁移到 C 区）

## 阶段五：持久化快照

- 保存当前有效的引擎路径快照，用于后续对比

## 阶段六：A 区全量扫描与索引建立

- 批量遍历所有 A 区目录，使用多线程并发读取 .strm 文件（4 个工作线程）
- 解析 .strm 文件内容，提取云端 WebDAV 路径
- 启动时使用 bulk_connection 长连接模式批量写入数据库（绕过 rw_lock，复用连接），扫描完成并提交后一次性重建 FTS 索引
- 定期刷新时使用 upsert_a_batch（保持线程安全，逐批维护 FTS）
- 每 1000 条批量写入一次数据库
- 批量预读 `IN(...)` 按 900 条/批 `chunk_list` 分片，规避 SQLite 变量上限（区别于每 1000 条一次提交的提交语义，两参数独立）
- 每 100 条或每 2 秒输出进度日志（含 records/s 性能基准），解决日志冻结问题

## 阶段七：A -> B 全量同步

- **启动时使用 `bulk_connection()` 长连接模式**（1 个连接 + 1 次提交），跳过血统校验和 per-file `check_exists` HTTP
- **预加载缓存**：ghost 保护和 B 区指纹到内存缓存
- **双模式提交**：`use_bulk=True` 单事务提交（首次启动，无并发），`use_bulk=False` 分批提交（每 1000 条，主动刷新，有并发）
- **指纹防重复制**：遍历 A区 记录。程序只会把**指纹完全不存在于 B区 数据库**的 A区文件复制到 B区。
- **命名保护**：如果该指纹在 B区 已经有了对应的 `valid` 实例（即使物理文件名不同），程序会判定此文件在 B区 已经有更优命名（如用户重命名整理过的名字），**直接跳过复制**，防止劣质原名文件反复回灌、污染媒体库。
- **并发安全设计**：`_sync_one_record` 不使用指纹锁，依赖三层防御（内存缓存 + 文件系统检查 + 去重清理）。添加指纹锁会引入性能灾难（阻塞 watchdog），且 `b_fingerprint_exists` 看不到 `bulk_connection` 的未提交写入。详见 `wiki/Core-Sync-Engine.md` 的"并发安全设计"章节。

## 阶段八：启动 Watchdog 监控与主动刷新定时线程

> **设计原则：冗余清理永远只在局部触发，不做全盘扫描。** 启动时不再执行 `cleanup_a_redundant_using_api()` 和 `cleanup_b_redundant()`。冗余清理改为运行时按需触发：WebUI 手动刷新媒体时、watchdog 检测到 A/B 区文件删除时（通过 `trigger_delayed_cleanup`）。

### 周期性主动刷新与 mapping-scoped 扫描

- **主动刷新触发**：定时线程周期调用 `refresh_service` 的 `scan_and_sync`，根据 `refresh_paths` 配置的 STRM 入口路径执行 A→B 增量同步
- **mapping-scoped 扫描**：`get_a_roots_for_refresh_paths` 根据当前生效的 `a_b_mappings` 决定本次扫描的 A 根子集。每个 `refresh_path` 必须能唯一映射到某个 A 区根目录；若映射无法唯一确定（多根共享同一入口），该路径将被 **fail-closed 跳过**，并在日志中登记跳过原因
- **refresh_paths 为空时**：程序跳过周期性扫描，但 B 区删除联动（用户手动删除 B 区文件触发云端删除）仍然正常工作

### 冗余清理的 fail-closed 策略（`/api/fs/list` 假阴性防护）

无论是 A 区冗余清理（`cleanup_a_redundant_using_api` → `_collect_cloud_files_concurrent`）还是 B 区僵尸清理（`cleanup_b_zombies_under_folder` → `_collect_cloud_files_in_directory`），都通过共享校验函数 `_parse_fs_list_content` 按 `docs/openlist_api_fs_list_contract.md` 判别契约执行 **fail-closed**：

- 网络异常、非成功 code、`data`/`content`/`total` 缺失或类型不符、`content=[]` 但 `total>0`、分页中途任一页失败、100 页安全阀耗尽 —— 一律视为**不可信**，该父目录下的本地记录**整组不参与冗余差集**，确保不会因网络假阴性误删 A 区物理文件、误删 DB 行或误加 ghost 保护。
- 仅"权威成功"（HTTP 200 + 业务 code ∈ {0,200} + data 为 dict + content 为 list + total 为非负 int）可作为权威目录快照；仅"成功空目录"（`content==[]` 且 `total==0`）可判定本地记录为冗余/僵尸。

## 三、 字幕文件处理流程

## 1. 触发时机

- 启动后由 `_scan_a_subtitles_on_startup()` 单独扫描（`initial_scan_a()` 仅批量索引 STRM，不处理字幕）
- Watchdog 监听到 A区字幕文件新增/修改时（`handle_a_created_or_modified`）

## 2. 处理流程

- 使用 `subtitles` 表记录：本地路径、目标路径、指纹、季、集、语言代码、状态
- 避免重复处理，支持目标文件丢失后的重新生成

## 四、 异常与重复文件隔离机制

## 1. 重复文件隔离 (`.duplicate`)

在运行期间，如果 Watchdog 监听到 B区 突然被拷入了重复指纹的文件：

- 评分低（非标准命名）的文件会被 `quarantine_file` 改名为 `xxx.strm.duplicate`。
- 该文件会在下一轮刷新或延迟自愈周期中，被阶段八的清理逻辑彻底物理抹除。

## 2. 损坏与空文件恢复机制

如果 B区 某个 STRM 文件内容被意外修改或置空，导致程序无法解析其 WebDAV 路径：

1. 监听触发。
2. 检索数据库，寻找该物理路径的历史指纹与 A区 源路径。
3. 如果在 A区 找到了原始源文件，立即调用 `shutil.copyfile` 进行**物理恢复**，恢复其 `valid` 状态。
4. 如果 A区 也没有对应源文件，判定为无法挽救的损坏文件，改名为 `xxx.strm.invalid`，标记为 `quarantined`，留待人工排查。

## 3. 单兵越界观察机制

当 B区 某文件被移动到疑似非法位置时：

1. 触发 30 秒延迟观察（`trigger_delayed_solo_check`）
2. 观察期内若有其他同指纹文件跟进，判定为合法批量操作
3. 观察期结束仍只有单文件，且云端有多集 → 物理删除并从 A区恢复
